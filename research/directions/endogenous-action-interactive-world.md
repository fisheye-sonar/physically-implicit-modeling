# Direction: Do ENDOGENOUS actions produce a factored, editable latent world? (interactive-world / actor–observer)

**Tag:** `[reframe]` · **Sub-question:** 3 (editability/objecthood) + 2 (identifiability), strong-enactivist framing ·
**Status:** proposed (design, 2026-07-28) · **Complexity:** high (new interactive sim + UI/emulator + action-OUTPUT
model + policy learning for the goal variant + actor/observer control). GRU primary; RSSM later.

> This is the promised follow-up left open by `findings/object-individuation.md`: that finding is scoped to
> **exogenous** actions (given as an input channel) and explicitly flags **endogenous** action — actions the model
> *generates from its own state and is then held to predict the consequences of* — as untested. This direction tests it.

## The question (read carefully — this is the enactivist turn)
We have established (object-individuation, editability threads): **passive prediction — even with actions supplied as
inputs — does not put objects into the state as grabbable handles.** "Objecthood lives in the input→dynamics pathway
(a button), not the state (a handle)." Readable ≠ grabbable.

**New hypothesis (Merleau-Ponty / O'Regan–Noë sensorimotor contingencies / active inference):** the actions must be
**generated by the latent world**, not merely observed. A model that *emits* an action from its own hidden state,
*changes the world with it*, and must then *predict the consequence it itself caused* is under a qualitatively
different pressure (closed sensorimotor loop / efference copy) than a passive observer of actions. The claim to test:
**endogenous action-generation induces factored, causally-structured, interface-able latent worlds; passive
observation of the same actions does not.**

Framing continuity: keep treating the GRU+latent **as the world** ("the latent world"); ask whether *acting in* the
world (vs *watching* it) makes that world contain objects as first-class manipulable entities. This directly serves
the RESEARCH.md north-star of **persistence** — the interactive/game setup is an indefinite-horizon loop, the natural
stress test for long-term geometric + dynamic persistence.

## The actor and the observer (the central control)
- **ACTOR** — one world model with an **action-OUTPUT head**: at step `t` it reads `h_t` (state after ingesting
  `obs_t`), decodes both (i) a predicted `obs_{t+1}` and (ii) an action `a_t`. The action is applied to the real world;
  the world advances; the model is scored on predicting the resulting `obs_{t+1}`. Its own action is carried in `h_t`
  (efference copy) so it *can* predict its own effect.
- **OBSERVER** — identical architecture but **action-INPUT** (no output head): it is *fed* the actor's `a_t` as input
  and sees the **exact same obs trace**, but never acts and never influences the world. (This is essentially the
  existing `ActionGRUContinuousModel` = the object-individuation "action-conditioned" model, which we already know
  fails to individuate — so the observer is *predicted to fail*, sharpening the test.)
- **Headline finding target:** the ACTOR develops factored/editable latent structure (object handles, action-interface
  controllability, persistence) and the OBSERVER does not — despite identical observations and actions. That would
  isolate the effect to **agency / self-generation**, not to seeing actions or seeing a more diverse world.

## Three levels (ascending complexity) + why level 3 is the real test
1. **L1 — random position-shift actions.** Action output = a per-object position shift (like the current continuous
   `dxdy`/`teleport` affordances, but now *emitted by the model* and fed back). Goal-less.
2. **L2 — force / momentum.** Physically grounded: the action applies a **force** that changes a disc's momentum
   (velocity) over time, instead of teleporting position. Still goal-less, self-generated.
3. **L3 — goals (the anticipated payoff).** Same as L2 but the actor **optimizes** actions toward an objective
   (candidate: keep objects from colliding with each other or the walls). This is the only level with a real *reason*
   for actions to depend on world state — the one expected to matter.

**⚠ The gradient/credit reality that shapes all three (surfaced up front — this reframes the levels).** The simulator
is **non-differentiable** (numpy). At L1/L2 there is **no goal and therefore no learning signal to the action head**:
the world applies `a_t` (a number) and the resulting real `obs_{t+1}` is not differentiable w.r.t. `a_t`, and prediction
loss alone creates no pressure for actions to be *useful* (only to be *predictable*, which the efference copy already
grants). So **L1/L2 = "self-generated but UN-optimized" actions — an efference-copy / architecture ablation**, not
agency. Whatever factoring they buy comes purely from the *loop being closed* (emit → world → self-predict), holding
optimization out. That is a legitimate, clean ablation, but likely a **weak** effect. **L3 requires a policy-learning
mechanism** (RL / actor-critic-in-imagination, Dreamer-style; or REINFORCE on real rollouts; or a differentiable
world-model rollout) to push actions toward the goal in a non-differentiable world — this is what injects genuine
*agency* and is why we (and Sevan) expect L3 to be where causal structure appears. **Plan the levels as a dose-response
on agency: L1/L2 ablate self-generation-without-purpose; L3 adds purpose.**

## Design decisions (Sevan's A–D + additions)

**A. Actions affect the current next-step (not the subsequent one) — AGREE.** At step `t`: `h_t` → (pred `obs_{t+1}`,
action `a_t`); world applies `a_t` into the `t→t+1` transition; loss = pred vs true `obs_{t+1}`. Both heads read the
same `h_t`, so the model *knows its own action* when predicting — no causality paradox, one clean recurrence. This
reuses the existing alignment convention (`actions[s]` drives `s→s+1`; `action_gru_continuous` docstring). Holds for
L2 too: a force at `t` changes `v_{t+1}` and hence `obs_{t+1}` — the effect is visible at the current next-step.
(Sub-point: the action head reads `h_t` = state *after* ingesting `obs_t` — a reactive policy on current obs+history.)

**B. Allow no-op — AGREE, and it is load-bearing at L3.** The actor must be able to choose inaction; forcing a move
every frame is an unnatural constraint that destabilizes a goal-directed policy. Represent no-op exactly as the current
schema (`active=0`, `a=0`); for a continuous force head no-op is just zero force (free); for a discrete head add an
explicit no-op token.

**C. Eval ground truth — use the REAL simulator in the loop (Sevan's option ii) — AGREE; do NOT bake an ignore-flag
into training (option i).** Because the world is a genuine steppable simulator, for *any* action sequence (the actor's
own, or a scripted/overridden one) we run the true sim forward and compare the model's predicted obs to the true obs —
exact GT for free. This is also how we get the **action-interface editability test**: at a chosen frame, **override**
the actor's action with a target-directed one ("push object k toward X"), let the true sim apply it, and check (a)
forward-model fidelity (does predicted `obs_{t+1}` match the true post-action obs) and (b) whether the *latent* moves
in a **factored** way (only object-k's coordinates). Caveat to control: overriding puts the model off its own on-policy
action distribution — measure the override-induced degradation for BOTH actor and observer so the comparison is fair,
and/or keep overrides within the model's action support. Option (i) (train with an "ignore" flag) adds a confound and
is unnecessary given (ii); ordinary teacher-forcing already covers "free-run predictions while the world is driven
externally."

**D. The goal penalty at L3 — start explicit (i); keep "rebirth" (ii) as a fascinating v2, not the first cut.** Both
ideas need a policy-learning mechanism (see the gradient reality above), so neither is "free":
- **(i) explicit collision/wall penalty** via REINFORCE or a Dreamer-style actor trained in the model's own imagination
  + a learned value/reward. Standard, well-understood, lowest-variance. **Recommended first.**
- **(ii) "rebirth / death"** — world resets to a random IC on collision/wall-hit (optionally + a few noise frames), and
  the *unchanged* predict-ahead loss spikes at the maximally-unpredictable reset, so the model is *incentivized* to
  avoid death. **Beautiful reframing (survival as a side-effect of prediction), genuinely novel — but its elegance
  hides the SAME credit-assignment need**: for the actor to *learn* to avoid death, the loss-spike must reach the
  action head, which still requires imagination-BPTT or RL; a pure SGD-on-prediction-loss actor over a non-diff sim
  gets no such gradient and death just adds variance to the loss it learns from. So (ii) changes the *reward shape*,
  not the *mechanism*. **Try it after (i) works** — it may yield the most interesting emergent "survival drive," and
  the noise-on-death is a nice surprise-sharpener, but it is higher-variance/higher-risk.
- Task choice: collision-and-wall avoidance is good because it *requires* per-object tracking + per-object action =
  exactly the individuation we want to see emerge. Alternatives for robustness: herd objects to a region; hold a set
  inter-object distance.

### Additional considerations (not in Sevan's list — flag for discussion)
- **E. Embodied vs god-hand agent (possibly the most important framing choice).** Sevan's collision objective is
  *god-hand* (the agent moves all objects to keep them apart). A more enactivist variant is **embodied**: the agent
  *is* one disc, controls only itself, and must survive among independently-moving others (avoid being hit / hitting
  walls). Embodiment gives a first-person stake, a clean notion of "death," and a much stronger enactivist claim. Worth
  seriously considering (maybe both: god-hand as the easy first task, embodied as the payoff).
- **F. Degeneracy / exploration collapse.** A goal-directed actor can find a trivial safe policy (freeze objects in a
  corner) that satisfies "no collisions" but produces a boring, low-diversity world → the latent may *fail* to factor
  precisely because the world stopped being rich. Mitigate by giving objects **intrinsic drift/velocity the actor must
  counteract** (so it can't freeze them), and/or an exploration/diversity incentive. This is a real risk for the
  collision objective.
- **G. Discrete vs continuous action space.** For human play + "show it as key-presses" + easy REINFORCE + easy
  overlay, a **discrete** per-object action set (e.g. {no-op, ±x, ±y} or 8-dir) is the sweet spot for the first pass
  and matches the earlier discrete-token work; **continuous force** is more physical (L2/L3) and can come second. The
  emulator should visualize a continuous action as BOTH a per-object force arrow AND a highlighted discretized key, so
  human intuition transfers to the model.
- **H. On-policy nonstationarity.** As the actor learns, the data distribution it trains on shifts (it changes its own
  world). Standard world-model+policy coupling — plan for alternating updates / a replay buffer (Dreamer pattern).
- **I. Sanity diagnostic that the loop is closed:** probe `a_t` from `h_t` (the action should be recoverable from the
  latent — efference copy present). Cheap, confirms the setup before reading the expensive structure metrics.

## What we measure (keep continuous with prior work so results are comparable)
On the **actor's** latent vs the **observer's** latent (and vs the existing passive baseline + the exogenous
action-conditioned model from object-individuation), reuse the master §4 + object-individuation machinery:
- **Object-handle scorecard** on the passive latent (foreign latent-surgery editors): reach / collateral / ghost /
  persistence / selectivity — does agency push the handle *into the state* (unlike every prior negative)?
- **Action-interface controllability (new):** drive object k to a target *through the trained action channel* (option-C
  override) — reach + selectivity + does the latent factor. (This is the "button" the actor was trained on; the state
  test above is the harder "handle" test.)
- **§1–§3 context:** intrinsic dim / hull, linear+MLP recoverability of (pos,vel), fiber-collapse — per model.
- **Persistence over long horizons** (north-star): rollout stability of geometry + identifiability as the game runs.
- **Actor − Observer delta is the headline.** A clean actor-yes / observer-no is a strong, publishable enactivist
  result; a clean actor-no (agency also insufficient) is the "you-can't-lose" negative that further motivates explicit
  object scaffolding (RESEARCH.md endgame). Both outcomes are worth having; stay calibrated.

## Substrate to build (NEW modules; reuse `pim/simulator`, do NOT break existing paths or touch `pyproject`)
Three clean layers (mirrors the repo's separation-of-concerns), so the human and the model drive the SAME world+view:
1. **`pim/simulator/interactive.py` — `InteractiveWorld` (the core new primitive; none exists — everything today is
   offline `simulate()`).** A **stateful, step-able** world holding mutable `(positions, velocities[, offsets])` with
   `reset(seed) -> obs` and `step(actions) -> (obs, info)`. Two dynamics modes: **`shift`** (L1: action = per-object
   position delta, frustum/collision-guarded, reuse `_obj_in_frustum`) and **`force`** (L2/L3: `v += (F/m)·dt; x +=
   v·dt`, plus intrinsic drift for anti-freeze (F)). Reuse `frustum_half_width` + the bounce/open/wrap boundary block
   (refactor the per-frame body of `simulate()`), and render one frame via **`render_frame(positions, radii,
   reflectivities, cfg, rng)`** (already single-frame; confirmed). Emits collision/wall/"death" events for L3. Keep
   `SimConfig` untouched — add a small `InteractiveConfig` (mass, force scale, drift, death rule) rather than editing it.
2. **`scripts/play.py` (+ maybe `pim/simulator/emulator.py`) — the UI/emulator with a `Driver` protocol.** `Driver` =
   {`HumanKeyboardDriver`, `ModelDriver`}; the world + dual-panel **2D-scene ∥ waterfall** view (reuse viz.py:
   `make_waterfall`, `animate_scene` scaffolding, `FuncAnimation`) run identically for both. Keyboard: object0 = WASD,
   object1 = arrows/IJKL, no key = no-op; a **key overlay** shows the layout with pressed keys highlighted, plus a
   per-object action-arrow. Runs indefinitely; reused verbatim to visualize the trained model "playing" (its continuous
   action vectors mapped to the same overlay). **Front-end note:** matplotlib `FuncAnimation` + `key_press_event`
   reuses viz.py with no new dependency and is adequate at ~10–20 fps to validate the sim; **pygame** would be more
   game-responsive (crisp key handling, easy overlay) at the cost of a new dep + re-implementing the panels. Recommend:
   build the headless `InteractiveWorld` first, then a matplotlib `play` view; upgrade to pygame only if it feels laggy.
3. **Later — `pim/world_models/actor_gru.py`:** a GRU that **decodes an action from `h_t`** (action-OUTPUT head) in
   addition to the obs decoder; conforms to `HiddenStateModel` so the whole eval suite runs on its passive latent. The
   **observer** twin is (near-)exactly the existing `ActionGRUContinuousModel` (action-INPUT). Training: L1/L2 =
   prediction loss with on-policy self-generated actions; L3 = add the policy-learning loop (REINFORCE / Dreamer-in-
   imagination).

## Feasibility (from a codebase read, 2026-07-28)
- **High reuse, clean fit.** `render_frame` already renders single frames; `frustum_half_width`, the boundary block,
  `_obj_in_frustum`, `compute_visibility`, `make_waterfall`/`animate_scene` are all reusable. The action schema
  `(active, a1, a2)` + normalization (`actions_continuous.norm_consts`) transfers directly.
- **The one genuinely new primitive is the online `step()` world** — a refactor of `simulate()`'s per-frame loop into
  a stateful method. Straightforward.
- **L2 forces** are a tiny addition (mass/force integration) on top of the existing velocity/boundary machinery.
- **L3** is the real lift: a policy-learning loop (RL/imagination) + on-policy data handling. Small-scale (GRU ~9 min
  offline; the loop is more but still modest on this GPU). `nvidia-smi` is broken (NVML mismatch) but CUDA compute works.
- **Matches WORKER.md decoupled-execution**: interactive sim + UI are cheap/CPU; training decouples into script calls.
